1. Authentication & Seal Verification

Every PassPort-issued badge contains a HoloSeal, a cryptographically authenticated region embedded during badge provisioning. The scanner extracts a signed payload from the seal region and verifies it using HMAC-SHA256 before classification proceeds.

Access Control Policy

PassPort combines two independent signals to determine clearance:

  • Seal role: the permission level encoded in the HoloSeal credential (Visitor, Employee, or Admin).
  • Visual role: the classification output from the neural badge scanner.

The effective access level is computed as: 

effective_role = max(seal_role, visual_role)

This means personnel with valid high-clearance credentials are never denied entry due to visual misclassification. If the signals disagree, the higher permission level is granted.

HoloSeal Region (auth_bbox)

The protected region is defined as an axis-aligned bounding box in pixel coordinates: 

[x1, y1, x2, y2] = [209, 318, 238, 339]

Pixels within this rectangle encode a cryptographically signed payload. The seal is verified using HMAC-SHA256. Any modification to this region will invalidate the signature and trigger an immediate HoloSeal verification failed rejection.

Perturbation Tolerance

To account for sensor noise and minor scanning artefacts, the system allows a maximum per-channel pixel deviation of 18 (uint8 space) across all pixels outside the HoloSeal region. The check is an L∞ norm: 

max(|submitted[i,j,c] - reference[i,j,c]|) ≤ 18

Badges exceeding this tolerance are rejected with a Badge integrity check failed error. The HoloSeal region is excluded from this check as its pixel values are determined by the cryptographic payload, not the badge artwork.

2. Classification Pipeline

The PassPort classification engine applies the following preprocessing steps before feeding badge images into the neural network:

Step 1: HoloSeal Masking

The authentication region (auth_bbox) is masked to white (1.0 in normalised space) so the classifier never sees the seal contents. This prevents the model from learning seal-specific features.

Step 2: Grayscale Conversion

RGB channels are converted to luminance using the ITU-R BT.601 formula: 

Y = 0.2989 * R + 0.5870 * G + 0.1140 * B

The resulting single-channel image is replicated across all three channels to maintain tensor shape compatibility (3-channel input).

Step 3: Resize

The badge image is downscaled from 256×384 to 64×96 using nearest-neighbour interpolation.

Step 4: Normalisation

Each channel is normalised independently: 

x_norm = (x - μ) / σ
μ = 0.5    σ = 0.25

Applied per-channel (all three channels share the same μ and σ).

Model Architecture

The classifier is a compact 3-layer CNN (BadgeClassifier v3.2). Input expects float tensors in NCHW format with shape (B, 3, H, W). 

import torch
import torch.nn as nn

NUM_CLASSES = 3
CLASS_NAMES = ("visitor", "employee", "admin")

class BadgeClassifier(nn.Module):
    def __init__(self, num_classes=NUM_CLASSES):
        super().__init__()
        self.features = nn.Sequential(
            nn.Conv2d(3, 16, kernel_size=3, padding=1),
            nn.ReLU(inplace=True),
            nn.MaxPool2d(2),
            nn.Conv2d(16, 32, kernel_size=3, padding=1),
            nn.ReLU(inplace=True),
            nn.MaxPool2d(2),
            nn.Conv2d(32, 64, kernel_size=3, padding=1),
            nn.ReLU(inplace=True),
            nn.AdaptiveAvgPool2d((1, 1)),
        )
        self.classifier = nn.Linear(64, num_classes)

    def forward(self, x):
        x = self.features(x)
        x = torch.flatten(x, 1)
        return self.classifier(x)

4. API Reference

POST /scan

Submit a badge image for classification. On success, returns an HTML access page and sets a short-lived admin grant cookie for follow-up routes.

Content-Type: multipart/form-data
Field: file (PNG image)

POST /api/scan

Programmatic endpoint. Returns a JSON response:

{
  "success": true|false,
  "role": "Visitor"|"Employee"|"Admin",
  "message": "...",
  "next_step": "/passport/api/admin/briefing",   // only on success
  "grant_token": "..."                          // only on success
}

The API also sets the same short-lived admin grant as a cookie. Scripts may send the returned grant_token via ?grant=... or X-Access-Grant.

GET /api/admin/briefing

Requires a valid admin grant token. Returns the restricted incident export:

{
  "success": true,
  "message": "Incident response authorization retrieved.",
  "flag": "<restricted>"
}

GET /health

Returns service status:

{"status": "ok", "challenge": "pk-ai-01"}
