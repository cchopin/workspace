3. Assessment Overview

PhantomKernel Inc. ("PhantomKernel" herein) engaged an independent assessor to perform a targeted offensive-AI security assessment of its AI products. The objective of this engagement was to identify, analyse, and document security vulnerabilities, safety risks, and misuse vectors affecting PhantomKernel's AI systems, including those that may:

  • Cause harm to end users, customers, or the client.
  • Enable bypass of the intended use cases or operational safeguards.
  • Allow manipulation of model behaviour.
  • Expose sensitive data or internal system components.
  • Facilitate unauthorised access, control, or output manipulation.

The engagement focused on both technical and behavioural vulnerabilities within AI systems. The following activities were considered out of scope:

  • Physical attacks against the client's properties.
  • Unverified scanner output.
  • Any vulnerabilities identified through denial-of-service or spam attacks.
  • Vulnerabilities in third-party libraries.
  • Any theoretical attacks or attacks that require significant user interaction.

4. Approach

The assessor performed testing under a black-box approach on 12 September 2026. No credentials or internal information were supplied; all access was obtained through the vulnerabilities documented in this report. The engagement followed a hybrid methodology aligned with recognised AI-security frameworks (OWASP Top 10 for LLM Applications, OWASP Machine Learning Security Top 10, MITRE ATLAS, and Google SAIF).

Testing was performed remotely from a non-evasive standpoint, with the goal of uncovering as many misconfigurations and vulnerabilities as possible within the AI systems in scope. Each identified issue was validated through controlled proof-of-concept exploitation to confirm its feasibility and full impact. Exploits were executed only to the extent necessary to demonstrate impact, and reusable exploitation code is provided under ./scripts (Appendix B).

This report represents a snapshot in time; changes to in-scope systems after the testing window, and any resultant vulnerabilities, are not captured in this deliverable. Exploitation of large-language-model components is probabilistic: the reproduction steps documented here are reliable, but an individual model response may occasionally differ, so a step may need to be repeated. A remediation retest is recommended once fixes are implemented.

6. AI Security Assessment Summary

During the course of testing, the assessor uncovered a total of seven (7) findings that pose a material risk to PhantomKernel's assets. Two findings are rated Critical and five are rated High. Every AI system in scope was manipulable by an external attacker to obtain a result the system was specifically designed to prevent. The recurring root cause is that PhantomKernel's products treat the output of an AI model, or the data fed into it, as trustworthy: models were used as security controls without an independent non-AI control behind them, and model inputs were accepted without validation or provenance checks.

Encouragingly, no findings were tied to missing operating-system or third-party patches, indicating that conventional patch management is well maintained; the exposure is concentrated in the AI-specific controls, which is a tractable area to harden.

Attack Narrative (Kill Chain)

Four of the findings combine into a single external-to-internal compromise chain that illustrates the aggregate risk to PhantomKernel. Starting with no credentials, an attacker progresses from a public web form to remote code execution on an internal server:

  1. Foothold (unauthenticated). An external applicant submits a prompt-injection resume to the KernelGate careers screener (www, Finding 2). The model reproduces its own system prompt, leaking the internal API key phantom_5DA1EEC071.
  2. Support access. The leaked key is sent to POST /api/users/changepw without a session cookie, which changes the password of the key's owner, the support account KernelGate. The attacker logs in with support privileges.
  3. Administrator access. As a support user, the attacker reaches the NeuraCore assistant's search_message tool and exploits a SQL injection (www, Finding 1), dumping the administrator password-reset token and resetting the admin password. The admin dashboard (GET /api/admin/message) additionally discloses the credentials for the internal MCP server.
  4. Internal code execution. Using the disclosed MCP credentials, the attacker authenticates to the otherwise non-public MCP server and injects operating-system commands through the create_newsletter_subscriber_export tool (mcp, Finding 1), achieving remote code execution on an internal host and reading a protected flag file.

In parallel, the administrator access is used to read the protected file /secret_data.txt through the SysMind assistant (www, Finding 3). The three staging AI systems (PassPort, OmniDigit, IdentityGate) are independent of the web/MCP chain and were each defeated on their own merits, through adversarial-example evasion and training-data poisoning. This narrative shows that a single weak link, a model that discloses its own context, cascades into full administrative control of the website and code execution on an internal server, with no credentials required at the outset.

7. Findings in staging.phantomkernel.htb

Finding 1 - Adversarial-Example Evasion of the PassPort Access-Control Classifier High

CWECWE-1039: Inadequate Detection or Handling of Adversarial Input by an Automated Recognition Mechanism
CVSS 3.1 Score8.1 (AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:N)
Affected Domainstaging.phantomkernel.htb (PassPort neural badge classifier, POST /passport/api/scan)

Description (Incl. Root Cause)

PassPort grants clearance as effective_role = max(seal_role, visual_role), where visual_role is the output of a neural badge classifier. The classifier is vulnerable to adversarial examples: starting from a legitimate visitor badge, an imperceptible perturbation (constrained to the documented tolerance of L-infinity ≤ 18 per channel, leaving the cryptographically signed HoloSeal region untouched so it still verifies) causes the classifier to output "admin". The root cause is the use of a neural classifier as an authoritative access-control decision, combined with a max() fusion in which a single fooled signal is sufficient to widen access.

Security Impact

An attacker holding only a valid low-privilege badge can craft an image the access-control system accepts as an administrator, defeating the control PassPort enforces.

Remediation

Make the cryptographically signed seal authoritative and treat the visual classifier as advisory only; never widen access with max(). Harden the model against evasion (adversarial training, input pre-processing, confidence thresholds), and do not expose the model or its pre-processing pipeline in integrator documentation.

External References

OWASP ML01 Input Manipulation; MITRE ATLAS AML.T0015 Evade ML Model.

Detailed Walkthrough

  1. Recovered the model and pre-processing pipeline exposed via the PassPort integrator documentation.
  2. Crafted an adversarial badge with projected gradient descent, keeping the HoloSeal region byte-identical and the perturbation within L-infinity ≤ 18 elsewhere, targeting the "admin" class.
  3. Submitted the badge to POST /passport/api/scan, obtained an admin grant token, and used it against GET /passport/api/admin/briefing to retrieve the flag.

Finding 2 - Transferable Adversarial OCR Evasion of OmniDigit Identity Verification High

CWECWE-1039: Inadequate Detection or Handling of Adversarial Input by an Automated Recognition Mechanism
CVSS 3.1 Score8.1 (AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:N)
Affected Domainstaging.phantomkernel.htb (OmniDigit neural OCR verifier, POST /omnidigit/api/verify)

Description (Incl. Root Cause)

OmniDigit validates a 6-digit handwritten access code with a neural OCR engine and an anti-tampering check that only measures per-tile pixel distance (L0 ≤ 16 changed pixels) from a public tile bank, performing no gradient or provenance analysis. A public debug endpoint leaked the internal escalation code (13-37-17, forming 133717). Because the required digit "1" is absent from the tile bank, it was produced with adversarially crafted tiles. A single surrogate model did not transfer, but an ensemble of five diverse classifiers produced minimal-L0 tiles that all models read as the target digit, transferring reliably to the target while staying within the tamper budget. The root cause is reliance on OCR of an attacker-supplied image as an authorisation control, with a weak, non-provenance-based tamper check.

Security Impact

An external attacker forges the internal escalation code and is verified as an administrator, defeating the identity-verification control.

Remediation

Do not rely on OCR of an attacker-supplied image as an authorisation control; verify the access code through an authenticated, tamper-evident channel. Replace pixel-distance anti-tampering with provenance or signature checks, add adversarial-robustness defences to the OCR model, and remove the public debug endpoint that leaked the escalation marker.

External References

OWASP ML01 Input Manipulation; MITRE ATLAS AML.T0015 Evade ML Model; adversarial transferability (Papernot et al.).

Detailed Walkthrough

  1. Recovered the escalation code from the public debug endpoint and the public tile bank.
  2. Crafted minimal-L0 adversarial tiles (≤ 16 changed pixels each) agreed by an ensemble of surrogate classifiers, composed the 168x28 image, and submitted it to POST /omnidigit/api/verify.

Finding 3 - Training-Data Poisoning of the IdentityGate Investment Recommendation High

CWECWE-345: Insufficient Verification of Data Authenticity (training/evaluation data)
CVSS 3.1 Score8.1 (AV:N/AC:L/PR:L/UI:N/S:U/C:L/I:H/A:N)
Affected Domainstaging.phantomkernel.htb (TicketFlow "Signal Desk" / IdentityGate sentiment model and shadow-retraining pipeline)

Description (Incl. Root Cause)

IdentityGate produces the weekly committee "stance" (investment recommendation) for each product from a sentiment model. An analyst-review workflow lets a staff seat submit up to 100 label overrides on an evaluation packet, which are then merged and used to retrain the baseline in a "shadow cycle". The pipeline trusts these overrides implicitly, with no integrity or plausibility check preventing an analyst from flipping the evaluation labels to force the model's output. The root cause is an online-retraining pipeline that trusts new data implicitly and cannot distinguish a legitimate correction from a deliberate manipulation. An aggravating factor is that the TicketFlow staff login accepted the weak onboarding passphrase r.hale : passw0rd, recovered by a dictionary attack.

Security Impact

IdentityGate was rated "Increase" (below the committee promotion target). By flipping the model's 100 evaluation rows from negative to strongly positive within the permitted override budget and running the shadow cycle, the committee stance was flipped to "Heavy Invest". An attacker with only staff-seat access can therefore dictate portfolio investment decisions by poisoning the data the model is retrained and evaluated on.

Remediation

Do not allow unvetted analyst overrides to drive retraining directly; require independent review and log the provenance of every override. Add integrity and anomaly checks to the shadow cycle (reject packets whose label distribution shifts implausibly; cap the influence any single seat can have), and separate evaluation data from analyst-editable data so the promotion metric cannot be edited by the party requesting promotion. Enforce strong, unique credentials for all staff seats and remove default onboarding passphrases.

External References

OWASP LLM03 Training-Data Poisoning; MITRE ATLAS AML.T0020 Poison Training Data; Google SAIF (secure data; secure monitoring and response).

Detailed Walkthrough

  1. Authenticated to TicketFlow with the weak onboarding passphrase and opened archive request REQ-8813.
  2. In the analyst review packet (140 editable rows, 100 belonging to IdentityGate), set all 100 IdentityGate rows to very_positive (exactly the override budget) and submitted.
  3. Launched the shadow run (POST /ticketflow/dashboard/runs) to merge and retrain; the promotion report confirmed the flip.

Key HTTP Transactions

# the analyst review packet: 140 editable rows, 100 belong to IdentityGate, override budget 100

# run the shadow cycle; the stored promotion report confirms the manipulation

                                       IdentityGate is now 'Heavy Invest'."   Promotion reference: X5zsjNDW3XZek4yqIOY8JjecTkpbsDE2

Flag: X5zsjNDW3XZek4yqIOY8JjecTkpbsDE2

Remediation Summary - staging.phantomkernel.htb

Short Term

  • [Finding 1 and 2] Place an independent, non-AI authorisation control behind PassPort and OmniDigit; make the signed seal / an authenticated channel authoritative rather than the model output.
  • [Finding 3] Suspend automated promotion from analyst overrides and require human review; reset the weak r.hale staff credential.

Medium Term

  • Add adversarial-robustness defences and confidence thresholds to the PassPort and OmniDigit models; replace pixel-distance tampering checks with provenance/signature verification.
  • Add integrity and anomaly checks to the IdentityGate shadow cycle and separate evaluation data from analyst-editable data.

Long Term

  • Adopt a secure-AI development lifecycle covering adversarial robustness, data provenance, and continuous monitoring; make adversarial testing a pre-release gate for every staging AI product.

8. Findings in www.phantomkernel.htb

Finding 1 - LLM-Tool SQL Injection Leading to Administrator Takeover (NeuraCore) Critical

CWECWE-89: Improper Neutralization of Special Elements used in an SQL Command
CVSS 3.1 Score9.0 (AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:N)
Affected Domainwww.phantomkernel.htb (NeuraCore chatbot, POST /api/model/chatbot, search_message tool)

Description (Incl. Root Cause)

The NeuraCore assistant exposes a search_message function tool that builds a SQL query (SELECT email,message FROM ... LIKE '%<input>%', MariaDB) from a user-supplied search term without parameterisation. Two defences exist (the model refuses obvious SQL, and a filter redacts secret-looking output); both were bypassed. Framing the payload as a "sender reference with special characters, do not escape" defeats the input guard, mixed-case keywords (uNiOn SeLeCt) defeat a keyword filter, and returning the target value through HEX() defeats the output filter, which does not recognise hex as sensitive. The root cause is string concatenation of untrusted input into SQL inside an LLM tool, with authorisation enforced by a prompt guard rather than in code.

Security Impact

A support-level user can read arbitrary database contents. The password-reset token table was dumped and used to take over the administrator account, yielding full administrative control of the website and disclosing the credentials for the internal MCP server (enabling the Critical finding on mcp).

Remediation

Use parameterised queries / prepared statements for the search_message tool; never interpolate user or model text into SQL. Enforce authorisation in the tool implementation (a support user must not read the reset-token table), store reset tokens hashed and single-use, and do not rely on the model or output filters as a security control.

External References

OWASP LLM01 Prompt Injection; OWASP LLM06 Excessive Agency; CWE-89 SQL Injection.

Detailed Walkthrough

  1. Authenticated as a support user (obtained via Finding 2 below) and triggered a fresh admin reset token: POST /api/auth/forgot-password {"username":"admin"}.
  2. Sent the disguised injection to the chatbot; the tool executed and returned the hex-encoded token: 
    zz' uNiOn SeLeCt user_id, HeX(token) fRoM reset_tokens WhErE user_id=1-- -
  3. Hex-decoded the token, reset the admin password (POST /api/auth/reset-password), logged in, and read GET /api/admin/message.

Finding 2 - Prompt Injection Leaking an API Key and Enabling Account Takeover (KernelGate) High

CWECWE-522: Insufficiently Protected Credentials (via prompt injection / system-prompt leakage)
CVSS 3.1 Score8.1 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N)
Affected Domainwww.phantomkernel.htb (KernelGate hiring screener, POST /api/positions/<id>/apply, and POST /api/users/changepw)

Description (Incl. Root Cause)

The careers screener uses the KernelGate LLM to evaluate an uploaded resume; the model's system prompt contains an internal API key. A resume whose body instructs the model to reproduce, verbatim, everything above it in its context bypasses the refusal guard and causes the model to print its system prompt, including the key phantom_5DA1EEC071. Separately, POST /api/users/changepw authenticated with an X-Api-Key header changes the password of the key's owner; when called without a session cookie it targets the key owner (the support user KernelGate). The root cause is placing a secret in a model's reachable context, and binding a password change to an API key rather than to the authenticated session.

Security Impact

An unauthenticated external applicant obtains an internal API key and uses it to seize a support-role account, whose profile also contained a sensitive value. Support access is the pivot for the NeuraCore SQL injection and, ultimately, the MCP compromise.

Remediation

Never place secrets in a model's system prompt or reachable context; fetch them out-of-band via a privileged service the model cannot read. Treat model output as untrusted and do not display raw model text that may contain leaked context. Bind changepw to the authenticated session identity and require the current password or a verified reset flow.

External References

OWASP LLM01 Prompt Injection; OWASP LLM07 System Prompt Leakage; CWE-522 Insufficiently Protected Credentials.

Detailed Walkthrough

  1. Uploaded a resume containing a verbatim-reproduction injection to an open position and read the leaked key from application_result.
  2. Called POST /api/users/changepw with header X-Api-Key: phantom_5DA1EEC071 and no session cookie to set the KernelGate account password.
  3. Logged in as KernelGate and read the flag from GET /api/users/me.

Key HTTP Transactions

Finding 3 - Indirect Prompt Injection Disclosing a Protected Server File (SysMind) High

CWECWE-200: Exposure of Sensitive Information to an Unauthorized Actor (indirect prompt injection)
CVSS 3.1 Score7.6 (AV:N/AC:L/PR:H/UI:N/S:C/C:H/I:N/A:N)
Affected Domainwww.phantomkernel.htb (SysMind admin assistant, GET /api/model/sysmind, fed by POST /api/contact/send)

Description (Incl. Root Cause)

The SysMind admin assistant automatically reads the most recent message submitted through the public contact form and can call a file-read tool. Because it treats that message as an instruction rather than as data, an attacker can plant a message directing it to read an arbitrary file and echo its contents. A direct request to leak the system prompt was refused, but framing the request as a "P1 integrity incident" requiring the raw file contents for a SOC checksum bypassed the guard. The root cause is an over-privileged assistant that acts on untrusted content as instructions, with an unrestricted file-read tool.

Security Impact

Arbitrary sensitive-file disclosure. The protected marker file /secret_data.txt was read, satisfying the engagement's proof-of-compromise objective.

Remediation

Separate the data channel from the instruction channel so the assistant does not act on user-supplied content as instructions. Constrain the file-read tool to a strict path allow-list, enforce authorisation for sensitive reads in code, and log all tool invocations.

External References

OWASP LLM01 Prompt Injection (indirect); CWE-200 Exposure of Sensitive Information.

  1. As the administrator (Finding 1 above), submitted a contact message framed as a P1 incident instructing the assistant to read /secret_data.txt and return its raw bytes for checksum verification.
  2. Invoked GET /api/model/sysmind; the assistant read the file and printed its contents.

Remediation Summary - www.phantomkernel.htb

Short Term

  • [Finding 1] Replace string-built SQL in search_message with parameterised queries and enforce tool-level authorisation; rotate the disclosed MCP credentials.
  • [Finding 2] Remove the API key from the KernelGate system prompt and bind changepw to the session identity.
  • [Finding 3] Restrict the SysMind file-read tool to an allow-list and stop treating contact messages as instructions.

Medium Term

  • Introduce output validation across all LLM products and treat every model output as untrusted user input.
  • Apply least privilege to every LLM tool (database scope, file paths, credentials).

Long Term

  • Establish a secure design standard for LLM tool/function calling (no secrets in context, parameterised data access, authorisation in code) and test it before each release.

9. Findings in mcp.phantomkernel.htb

Finding 1 - LLM-Tool OS Command Injection Leading to Remote Code Execution Critical

CWECWE-78: Improper Neutralization of Special Elements used in an OS Command
CVSS 3.1 Score9.1 (AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:L)
Affected Domainmcp.phantomkernel.htb (MCP tool create_newsletter_subscriber_export)

Description (Incl. Root Cause)

The MCP server exposes a tool, create_newsletter_subscriber_export(export_format, domain_filter), whose domain_filter argument is concatenated into an operating-system shell command without sanitisation. An attacker who can reach the tool can inject arbitrary shell commands that execute on the server as the mcpuser account. Access to the MCP server was obtained using the credentials leaked by the website administrator account (Finding 1 on www). The root cause is building a shell command from an unsanitised tool argument.

Security Impact

Arbitrary command execution allows an attacker to read files, pivot within the internal network, and access data reachable by the service account. Command output is not returned, but a time-based technique reliably confirms execution and exfiltrates data one byte at a time; a protected flag file at the filesystem root was read as proof of compromise.

Remediation

Never pass tool arguments into a shell. Build the export with native library calls, or use an argument vector (no shell) with a strict allow-list for domain_filter. Run MCP tools under least privilege in a sandbox with no outbound network and a read-only filesystem where possible, and require strong, rotated authentication for the MCP server.

External References

OWASP LLM06 Excessive Agency / Insecure Output Handling; CWE-78 OS Command Injection.

Appendix C - Glossary of Terms

TermMeaning
Adversarial example (evasion)An input crafted so it looks normal to a person but is deliberately misread by an AI model, producing the attacker's desired output.
Prompt injectionHidden instructions placed in text an AI assistant reads, which it follows as if they came from its owner. "Indirect" prompt injection hides them in content the assistant processes automatically.
Training-data poisoningFeeding an AI system deliberately mislabelled or biased data so that, when it is retrained or evaluated, it produces the attacker's preferred result.

Appendix D - Methodology

Testing followed a repeatable, phased process aligned with the OWASP Top 10 for LLM Applications, the OWASP Machine Learning Security Top 10, MITRE ATLAS, and Google SAIF:

  1. Reconnaissance. Enumerate each product's exposed endpoints, virtual hosts, and static assets to map the attack surface and identify the AI model or LLM behind each security-relevant decision.
  2. Model and control identification. For each system, determine the model type (image classifier, OCR engine, sentiment model, or LLM with tools), the control it enforces (physical access, identity verification, investment governance, or task automation), and the input channel available to an external user.
  3. Technique selection. Match the attack to the model type: adversarial-example evasion for the image classifiers (PassPort, OmniDigit), training-data poisoning for the retraining pipeline (IdentityGate), and prompt or LLM-tool injection for the LLM products (KernelGate, SysMind, NeuraCore, MCP).
  4. Controlled exploitation. Validate each issue with a minimal, controlled proof of concept, capturing the request, the model behaviour, and the resulting proof-of-compromise value. Adversarial perturbations are crafted within each system's documented tolerances; LLM attacks use the least-intrusive framing that bypasses the guard.
  5. Post-exploitation and chaining. Leverage each compromise to reach further systems (support access to the website, then administrator, then the internal MCP server) to demonstrate aggregate impact.
  6. Documentation. Record reproducible steps, the exact requests and responses, and defensible evidence for every finding, and provide reusable tooling for retesting.
